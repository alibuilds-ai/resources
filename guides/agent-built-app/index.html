How I get an agent to build a working app in a day

The webcam app in the video took under ten hours, and almost none of that was me writing code. Most of it was deciding things before the agent was allowed to start. Here is the whole setup, stripped of anything specific to that app.

The reason this works is not that the model is clever. It is that an agent with a vague brief will produce something plausible and wrong, and you will not notice until you are four hours in. Every step below exists to remove one category of ambiguity before it can turn into code.

I ran this against a real problem: I wanted my iPhone's rear camera as a 1080p60 webcam, and the apps that do it charge monthly for that quality. The video covers the why. This page covers the how, and it applies to anything you would otherwise pay a subscription for.

The shape of it

The steps

  1. Write a PRD before you write a prompt

    Not a paragraph describing what you want. A document with a problem statement, a list of goals, and a list of non-goals. The problem statement should say what you already tried and what specifically failed, with the evidence. Mine recorded that the browser path tops out at 720p60 and silently drops to 30fps at 1080p, which is a WebKit limitation rather than a bug in the tool I was using.

    The non-goals list is the part people skip and the part that saves the most time. Every item on it is a feature the agent would otherwise build for you, unprompted, and then defend. Mine ruled out audio, the front camera, cloud relay, encryption, rooms, recording, Android, and App Store distribution. That is an enormous amount of work deleted in one sitting.

  2. Let something interrogate the plan

    A PRD written in one pass is full of decisions you did not realise you were leaving open. I use a skill that does nothing but grill me about it, question after question, until there is nothing vague left. It refuses to move on when an answer is hand-wavy.

    The output is a table. One row per question, the decision, and the consequence of that decision. Audio: none, which removes the audio session, the mic permission, and a whole class of interruption handling. Orientation: locked landscape, so no rotation logic exists anywhere in the codebase. Each row deletes work.

    The same session produces a second list that is just as useful: things that were in the PRD and are now cut, with the reason. I had planned a phase to reverse-engineer a network protocol. During the grilling it turned out an open-source client already implements that exact protocol in readable form, so the phase disappeared and was replaced by a reference section. That is a day saved by a question.

  3. Break it into phases with an observable finish line

    Each phase gets a "done when" that a person could check without reading any code. Not "signaling implemented" but "a browser at this address shows moving video from the phone, and resolution does not matter yet". Not "quality works" but "the app's own stats read 1920x1080 at 60 sustained, the throttling reason reads none, and the receiving end agrees".

    Order them so the riskiest, least understood part is first, with as little code around it as possible. If the part you ported blind is wrong, you want to find out in phase one while there is nothing else to blame.

  4. Run implementer and reviewer as separate agents

    The implementer writes the phase. A second agent then reviews that work against the PRD and the phase's finish line. I run the reviewer on the stronger model, because catching a subtle mistake is harder than making the change.

    Anything the reviewer finds goes back to the implementer, and the loop runs again. The phase is not finished when the implementer says it is finished. It is finished when the reviewer comes back with nothing. Only then does anything get committed, deployed, or built on top of.

    Keeping them separate matters. An agent reviewing its own work grades generously, and you get an approval that means nothing.

  5. Make the loop admit what it cannot check

    Some finish lines need physical reality. Mine included a thirty-minute soak test with the phone in hand, a real receiver running, and a latency measurement taken by photographing a millisecond timer. No amount of reviewing gets you that.

    So the rule is written down: a phase whose finish line needs hardware cannot be marked done by the loop, and the agent has to say so instead of quietly closing it. Without that instruction you get a green checkmark on something nobody has ever run.

  6. Keep the rules in a file, not in the chat

    Sessions end and context gets dropped. Anything you want to survive that goes in a constraints file the agent reads on every session: the hard limits, the working discipline, the loop itself. Mine says what must never change, that the app should fail loudly rather than silently downgrade quality, and that a changelog entry gets written in the same turn as the change rather than reconstructed from memory later.

    That last one sounds like bookkeeping. It is the reason I can tell you months later why a phase was deleted.

What actually made it fast

Ten hours of wall time, and the coding was the small part. The decisions table and the non-goals list are what kept the agent from building three things I would have thrown away. The reviewer gate is what stopped me from stacking a second phase on top of a broken first one, which is the failure that normally eats a weekend.

note

I am a software engineer, but I had never written a line of Swift and had never built a streaming app. Learning both properly would have taken weeks, and I would have given up and bought the subscription. The method is what closed that gap, not existing knowledge of the platform.

The pieces I used

For the video's build the local engine was VDO.Ninja, self-hosted on my own network. It already handles receiving a stream and handing it to whatever you are recording with, so the app I built only had to be a well-behaved publisher pointed at my own server. Worth checking before you build anything in this space, because a lot of the hard part may already exist and be free.

Everything else was Claude Code with the loop above, and one dependency in the app itself.

if you copy one thing

Copy the gate. A reviewer that can send work back, and a rule that nothing proceeds until it stops finding problems. The PRD and the phase list are what make the gate meaningful, but the gate is what turns a pile of generated code into something that runs.
